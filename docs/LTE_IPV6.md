# IPv6 через GSM-модем (GM510) — состояние и диагностика

> ТП сообщает: IPv6 через GSM-модем недоступен. Разбор по слоям — где именно
> может обрываться и как это проверить.

## Три слоя, где IPv6 может умереть

| Слой | Что нужно | Статус |
|---|---|---|
| 1. Оператор | IPv6 PDP-контекст в сети (APN с IPV4V6) | ❓ вероятный виновник (в РБ мобильный IPv6 операторы широка не дают) |
| 2. Модем GM510 | прошивка умеет IPv6 в NCM/ECM (PDP type IPV4V6) | ❓ проверяется AT-командами |
| 3. Роутер (наш образ) | `lte`/`lte6` на usb0, odhcpd, firewall v6 | ✅ готово: интерфейсы создаются при первом старте и добавлены в зону `wan` |

Наши патчи (`305a:1415` в `option.c`) дают AT-порты модема (`/dev/ttyUSB*`),
`cdc-ether`/`cdc-ncm` — сам `usb0`. Ничего доустанавливать не нужно.

## Диагностика на живом железе

### Шаг 1. Проверить, какие PDP-типы умеет модем

AT-порты: `/dev/ttyUSB0..2` (option-драйвер). Проще всего — `picocom`
(`apk add picocom` на extroot) или через `comgt`. Быстрый тест без терминала:

```sh
# на каком ttyUSB живёт AT-интерфейс — перебрать 0..2:
for p in /dev/ttyUSB0 /dev/ttyUSB1 /dev/ttyUSB2; do
  echo -e "AT\r" > $p; sleep 0.3; head -c 100 $p | strings
done
# ответ "OK" = AT-порт найден (обычно ttyUSB0 или ttyUSB2)
```

Затем (пример для порта AT на /dev/ttyUSB0):

```sh
apt=AT_CMD() { echo -e "$1\r" > /dev/ttyUSB0; sleep 0.5; head -c 300 /dev/ttyUSB0 | strings; }
AT_CMD "AT+CGDCONT=?"        # поддерживаемые PDP-типы: есть ли IPV6/IPV4V6
AT_CMD "AT+CGDCONT?"         # текущие контексты
AT_CMD "AT+CGPIAF=1,1,0,0"   # формат адресов (v6 readable), опционально
AT_CMD "AT+CGPADDR"          # выданные адреса
```

Если в `CGDCONT=?` нет `IPV6`/`IPV4V6` — прошивка модема v4-only,
путь закрыт до обновления firmware модема.

### Шаг 2. Если IPV4V6 есть — попытаться поднять

```sh
AT_CMD 'AT+CGDCONT=1,"IPV4V6","ваш-апн"'
# переподнять соединение (передёрнуть usb0 или перезагрузить)
# затем смотреть RA:
tcpdump -i usb0 -vv icmp6 2>/dev/null | grep -i 'router advert'
```

### Шаг 3. Роутер: интерфейс на модем

В образе это уже сделано: при первом старте создаются интерфейсы `lte`
(DHCP) и `lte6` (DHCPv6) на `usb0`, оба добавлены в зону `wan` — то есть
NAT и форвардинг работают. Проверить:

```sh
ifstatus lte6 | jsonfilter -e '@["ipv6-address"][0]'
```

Если нужен отдельный интерфейс с другим именем (например, `wan6`) — в LuCI:
Сеть → Интерфейсы → Добавить:

- имя `wan6`, протокол **DHCPv6-клиент**, устройство **usb0**;
- Firewall: зона **wan**.

Если RA от оператора придёт — IPv6 заработает без правки образа.

## Обходной путь: IPv6 поверх IPv4 (CGNAT-friendly)

Если оператор v6 не даёт вообще — туннель до своего VPS с IPv6.
В образе всё уже есть:

- **AmneziaWG/WireGuard** до VPS: на VPS поднять wg-сервер с `Address = 2001:db8::1/64`
  (ваш v6-блок), на роутере LuCI → AWG-интерфейс с Allowed IPs `::/0` —
  клиенты LAN получат v6 через туннель. Работает и за CGNAT.
- **sing-box** (vless/trojan на VPS) — то же самое, конфиг вручную.

Главное ограничение CGNAT-пути: входящие v6-подключения извне к вам не
пройдут (v6-адрес окажется за туннелем на VPS), исходящие — работают.

## Проброс портов через LTE — почему нельзя и что делать

**CGNAT**: оператор выдаёт приватный адрес (`10.x.x.x`/`100.64.x.x`),
наружу — общий NAT. Публичного IP у модема нет → DNAT-пробросы на роутере
не имеют входного адреса. Роутер тут не при чём: LuCI → Firewall →
Port Forwards работает, но целевой адрес за CGNAT.

Проверка: `ifstatus lte | jsonfilter -e '@["ipv4-address"][0]'` — если не
публичный (RFC1918/CGNAT-диапазон), входящих снаружи не будет.

**Варианты:**

1. **Статический «белый» IP у оператора** (IoT/бизнес-тарифы) — тогда
   Port Forwards заработают как есть.
2. **AWG/WireGuard до своего VPS** (всё вшито): роутер инициирует туннель
   исходяще (CGNAT не мешает), на VPS — DNAT нужных портов в туннель:
   ```sh
   # на VPS (nftables):
   nft add rule inet nat prerouting ip protocol tcp tcp dport 443 \
       dnat to <ip-роутера-в-туннеле>:443
   ```
3. **Tailscale/ZeroTier** в LXC-контейнере (LXC вшит) — доступ к сервисам
   без VPS, входящий трафик через их релеи.
4. **Cloudflare Tunnel** (cloudflared/sing-box) — исходящее соединение,
   входящие через CDN.
